# Existing erasure family: historical V1 matches after acknowledgement

Reproduced actual local handler requests with fake Auth/App Check verification and the existing in-memory RTDB adapter. New test `functions/test/round5-online-historical-erasure.test.js`: 1 pass / 2 fail / 0 skip. Both failures preserve `Retired history name` in the canonical and readable public result after actual successful deletion. The two-match case first verifies that the current latest result is correctly retired, then fails on the earlier acknowledged result. The deleted account's private leaf and public membership also survive there. The surviving peer remains a real participant and can still read that name. This is residual historical coverage of the existing account erasure family, not a separately counted new family.

The UI's current deletion contract says profile/progress/collection/social data will be deleted and makes an explicit retention exception only for purchase records. Existing `leaveAccount` already uses `Deleted player`, `deletedParticipants` and removes readable membership/private projection for the latest V1 result. Apply that same contract to every owned historical match while retaining anonymous match result and the surviving peer's projection.

Minimal compatible proposal:

1. Add `battleV1.eraseAccountHistory(uid, deletionRef)` in `battle-v1-friendly.js`; invoke it from `deleteAccount` immediately after existing `leaveAccount(uid)` and before deleting the user profile.
2. Canonical match envelopes contain JSON rather than indexed participant fields. A future-only participant index would miss the already existing records which reproduce this bug. Iterate `matchSecretsV1` with `orderByKey().startAfter(cursor).limitToFirst(5)`, process at most 40 pages and 15 seconds in one invocation. Persist `battleV1HistoryCursor` and `battleV1HistoryErased` on the existing private deletion workflow. This bounds memory, reads and work in each invocation and permits retry instead of an unbounded root read. No new client-readable tree or production rule is necessary.
3. For each owned match in the page, finish and settle it through current canonical transactions if needed; then apply the same `deletedParticipants[uid]=true`, `players[side].name='Deleted player'`, `stateVersion++` and paired projection publish as current `leaveAccount`. Remove its emotes. Preserve result, peer name/private state, rating receipt and monotonic projection version. An already retired canonical must still republish on retry so an interrupted projection cannot be skipped.
4. Advance the cursor only after all owned matches in a page are fully retired and published. After budget/deadline exhaustion throw the existing 503 `account-deletion-in-progress` error; actual deletion remains processing, leaving retry authorization and data available. Finish the checkpoint only once the tail is exhausted.
5. Relevant validation beyond the three current repros: already existing canonical envelopes without any new index; bounded multi-page scans with unrelated matches; failure after canonical retirement but before publish; checkpoint retry after a failed page; peer result/name/private projection preserved; canonical results identical; latest active match still follows normal deletion settlement. Existing metadata lifecycle guards fence new admissions after the deletion processing marker.

No production files changed while preparing this proposal. Root review/assignment is still required before implementing.
