## P1: a delayed enqueue retry permanently trapped an unrelated waiting player

`battle-v1-rollout.js` derives a match ID from requester UID and HTTP request ID. If the first enqueue committed, its response was lost, and the opponent resigned before the same request retried, terminal cleanup removed the active mappings. With a third player waiting, the retry committed a replacement reservation and active mappings at the old deterministic ID. `api.create()` then rejected the different participants with `MATCH_CREATION_CONFLICT`. The unrelated third player remained active against a canonical match that did not contain them. Their queue get, queue cancel and fresh enqueue all returned the same 409; normal maintenance could not resolve that replacement reservation.

The real handler path is reproduced in `functions/test/round3-online-enqueue-replay.test.js`: stubbed Auth/App Check boundary, real enqueue, real public resign, third enqueue, repeated original request header. A second ordering starts a same-ID request before the first canonical match exists and holds its control transaction until the twin request has created and finished the match. This demonstrates why a canonical pre-read alone is insufficient.

The root applied `enqueue-replay.patch`: canonical receipt replay before admission; requester UID and a random token on each queue reservation attempt; token-checked rollback that restores the same peer queue entry and returns the original receipt on collision; token-checked successful completion so an old completion cannot remove a newer attempt. It changes no result-acknowledgment latch and does not resurrect an acknowledged old result. Recovery checks the captured reservation token and individual active match IDs before removing anything.

Final unchanged six-case test against the exact original rollout module: **2 pass / 4 fail** (`enqueue-replay-baseline-exact-final.log`). Actual integrated source: **6 pass / 0 fail / 0 skip** (`actual-round3-online-enqueue-replay.test.js.log`). Controls cover a fresh new request, unchanged peer UID/player/deck/joinedAt/skill, pre-canonical concurrency, old successful completion versus a new token, a legacy record without token versus a new token, and conflict recovery preserving a newer attempt/active ID. The last two replacement controls inject the concurrent control state at the actual create-Promise boundary; they are adapter interleaving checks, not independent SDK observations.

## P2: a delayed terminal rating publication restored erased identity

`battle-v1-recovery.js` captured a valid committed account receipt, then wrote `battleV1Ratings/{uid}` after the users projection. A surviving peer's terminal settlement could pause before that public index transaction while the actual `deleteAccount()` workflow finished. The delayed transaction then recreated the deleted UID, original username, rating and game count after the complete tombstone. The production RTDB rules allow authenticated reads of this index, so filtering deleted players in the HTTP leaderboard did not erase the retained public data.

`round3-online-settlement-erasure.test.js` invokes actual account deletion while settlement waits before or after its rating transaction. Baseline control deletion after serial settlement and the after-write ordering pass; the before-write ordering restores erased personal data. The root applied `settlement-erasure.patch`, injecting the existing `writeAccountMetadata` lifecycle fence into recovery. Rating publication cleans up a late row and ignores only account deletion lifecycle errors, allowing deletion-internal settlement and the surviving peer to finish. Other publication failures still propagate and keep settlement retryable.

Final unchanged four-case test against the exact original index and recovery modules: **3 pass / 1 fail** (`settlement-erasure-baseline-exact-final.log`). Actual final source: **4 pass / 0 fail / 0 skip** (`actual-round3-online-settlement-erasure.test.js.log`). Assertions preserve the canonical deleted-participant flag, anonymized name, absent private/read membership, matching public/canonical version, surviving peer and complete settlement. A transient publication fault propagates, then retries without double rating or revision increments.
